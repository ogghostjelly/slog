# Variance

We have a function that takes two string slices.

```
fn foo<'a>(x: &'a str, y: &'a str) {}
```

and we call that function with a static string and a local string, using some fake syntax I made up for illustrative purposes.

```
const long: &'static str = "";
let short: &'local str = String::new();

foo(long, short);
```

When resolving the lifetime 'a, a naive borrow checker would see that 'static != 'local and refuse to compile.

But this is valid code! We'd like the borrow checker to realize that a &'static str can fit in places where a &'local str is required.

# Covariance

When a lifetime can shrink to fit. 'long <: 'short 

```
fn foo<'a>(x: &'a str, y: &'a str) {}
foo(long, short);
```
'static can become 'local because 'static is a subtype of 'local.

In type theory "is a subtype of" is represented with the sigil <: so 'long <: 'short. Its exactly like inheritance. A Cat can do anything an Animal can do because Cat is an Animal. 'long can do anything 'short can do because 'long contains 'short.

If a lifetime is a subtype of another lifetime, it's safe to shrink it.

# Invariance

When a lifetime cannot change.

```
fn foo<'a>(x: &mut &'a str, y: &'a str) {
    *a = b;
}
// Oh no! Setting a 'static to a 'local!
foo(&mut long, short)
```

long is supposed to live for 'static, but we just set it to a string that only lives for 'local! We want the compiler to reject this.

We want to say "when using &mut T, the lifetime of T can't change.". This is called invariance. We say &mut T is invariant over T.

In our code example, &mut &'static str is invariant over &'static str. The type of &'static str is not allowed to fit a &'local str, and the compiler successfully rejects the code.

Borrows are generic

&T has two generic parameters, imagine it as Borrow<'a, T>:
&'a T is covariant over 'a and covariant over T. In other words, 'a can change and T can change.

&mut T has two generic parameters, imagine it as BorrowMut<'a, T>:
&'a mut T is covariant over 'a but invariant over T. In other words, 'a can change but T can't.

Is this counter-example valid Rust?

```
foo(&mut short, long)
```
Answer Yes, it is! Even though short is behind an unchanging invariant reference (&mut), long is behind a changing covariant reference (&). The covariant 'static long can shrink to fit the invariant 'local short.

# Contravariance

When a lifetime can grow to fit. Fn('short) <: Fn('long)

The opposite of covariance. Only ever used in function parameters.

```
fn foo(f: fn(x: &'static str)) {}
fn bar(x: &'local str) {}
foo(bar);
```

If bar can handle a &'local str then it can handle a &'static str.

Fn(T) -> U is contravariant over T and covariant over U

# Multiplication Rules

In Fn(Fn(T)) what is the variance of T? Variance follows multiplication rules, where covariance = 1, invariance = 0, and contravariance = -1.

In Fn(Fn(T)), T is contravariant twice: -1 * -1 = 1, Fn(Fn(T)) is covariant over T.

# WTF? fn(&'a ()) -> &'a ()

This ones a bit obscure, I've only ever seen this in std::task::Context but I feel the need to explain it anyway.

If we have the type

```
type F<'a> = fn(&'a ()) -> &'a ()
```

The contravariant function argument fn(&'a ()) requires that F<'short> <: F<'long>.

The covariant return type -> &'a () requires that F<'long> <: F<'short>.

Both requirements F<'short> <: F<'long> and F<'long> <: F<'short> combine to make F<'a> invariant over 'a.

In the source code for std::task::Context:

```
struct Context<'a> {
    ...
    _marker: PhantomData<fn(&'a ()) -> &'a ()>,
    ...
}
```

This makes Context<'a> invariant over 'a.

This is almost the same as using *mut &'a () to force invariance, because *mut T is invariant over T.

```
struct Context<'a> {
    ...
    _marker: PhantomData<*mut &'a ()>,
    ...
}
```

But *mut T affects how auto traits are implemented (e.g Send/Sync), which is why it's not used.

If you don't know, an auto-trait is a trait that is automatically implemented for every type only if all of their fields also implement that trait, and *mut &'a () blocks some auto-traits from being implemented. See docs.
